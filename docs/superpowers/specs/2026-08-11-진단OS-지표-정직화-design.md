# 진단 OS 지표 정직화 — 설계

작성일 2026-08-11 · 상태: 승인됨(잭), 구현 계획 대기

## 왜 이걸 하는가

유입 작업(인스타 @coach_unick · 카카오 채널)을 시작하기 전에, **그 결과가 보이는 눈**을 먼저 만든다.
그런데 현재 대시보드를 열어보니 **보이는 숫자 중 하나가 거짓말을 하고 있었고**, 유입경로는 수집 코드가 있는데 한 건도 안 쌓여 있었다.

계보: 스폰지클럽 2기 마크(전준하) — *"애초에 확인하고 싶었던 지표를 재고 있지도 않았다"*(공유 수로 알던 게 사실 초대장 클릭이었음).
잭은 2026-07-19 3주차 순회에서 이미 같은 종류(CTA 추적 갭)를 한 번 겪었다.

## 실측 (2026-08-11, Supabase 직접 조회)

| 항목 | 값 |
|---|---|
| `diagnostic_results` 총 완료 | 16건 |
| 날짜 분포 | 07-20: 1 / 07-25: 1 / **07-26: 10** / 07-27: 1 / 08-04: 3 |
| 07-26 스파이크 비중 | 전체의 62% |
| 최근 7일(08-05~11) | **0건** |
| `cta_clicked = true` | **0건** (16건 전부 false, NULL 0건) |

**판정: 유입이 병목이다 — 단 완료 건수에만 근거한 판정이다.** 07-26 스파이크를 빼면 자연 유입 완료가 2주에 3건.
흐름 자체는 07-26에 10건이 완주된 것으로 정상 작동이 확인된다.
진입 수를 못 봤으므로 **화면 문제 가능성은 배제되지 않았다**(아래 「확인하지 못한 것」 참조).

## 확인된 결함 2건

### 결함 A — 「카톡 CTA 전환율」은 구조적으로 영원히 0%다

대시보드 숫자의 출처는 Supabase RPC `get_diagnostic_stats()`이고(레포에 소스 없음, `app/api/admin/stats/route.ts` 주석이 그렇게 적어둠), 그 안에서 `ctaRate`는 이렇게 계산된다:

```sql
'ctaRate', COALESCE(ROUND(100.0 * SUM(CASE WHEN cta_clicked = true THEN 1 ELSE 0 END) / NULLIF(COUNT(*), 0)), 0)
```

그런데 `lib/supabase.ts`의 `DiagnosticResultRow`(insert payload) 전체를 확인한 결과 **`cta_clicked` 필드가 없다.**
즉 **앱이 이 컬럼을 true로 바꾸는 경로가 코드에 존재하지 않는다.** 실제로 16건 전부 false다.

실제 CTA 클릭은 `lib/analytics.ts`의 `cta_kakao_click`으로 **Vercel Analytics에만** 쌓이고, 대시보드는 그것을 보지 않는다.

**결과:** 메모리에 "카카오 CTA 클릭 0건"으로 기록돼 유입 병목 판단의 근거 중 하나로 쓰인 그 0은, **실제 0이 아니라 측정 부재였다.**
(병목 판정 자체는 완료 건수만으로도 성립하므로 결론은 바뀌지 않는다. 다만 근거 하나는 무효다.)

### 결함 B — `lib/supabase-admin.ts`의 `getStats()`는 죽은 코드다

호출처 전수 검색 결과 자기 정의(`lib/supabase-admin.ts:62`)와 주석 한 줄(`app/api/admin/stats/route.ts:14`)뿐. 대시보드는 RPC를 쓴다.

그런데 이 죽은 함수 안에 **분자·분모 모집단 불일치**가 있다:

```ts
const total = baseRows.length;                                    // deep_stage_id null + full 제외
const deepCount = rows.filter((r) => r.deep_stage_id != null).length;  // 전체 rows 기준
const deepRate = Math.round((deepCount / total) * 100);
```

화면엔 영향이 없다(RPC 쪽 `deepRate`는 분자·분모가 같은 집합이라 정상). 문제는 **다음 사람이 이 코드를 읽고 "대시보드는 이렇게 계산한다"고 믿는 것**이다.

## 미해결 — utm이 0건인 이유를 아직 모른다

수집 코드는 있다:

```ts
// app/page.tsx:52-55
const params = new URLSearchParams(window.location.search);
if (key.startsWith("utm_") || key === "ref") utm[key] = value;
```

`lib/supabase-admin.ts:54`의 조회 컬럼에도 `utm`이 이미 포함돼 있다. 그런데 16건 전부 NULL이다.

| 가설 | 근거 |
|---|---|
| **(a) ref 붙은 링크를 배포한 적이 없다** | 유력. 지금까지 인스타 프로필·카카오 어디에도 `?ref=`를 안 붙였다 |
| **(b) 수집→저장 경로가 끊겨 있다** | 배제 못 함. 확인한 적이 없다 |

**(b)라면 유입경로 카드를 붙여도 영영 "미상"만 뜬다.** 그래서 카드 구현 전에 배선 실증이 선행된다.

## 설계

### 1. `ctaRate` 화면에서 제거 (잭 승인: "0이면 빼는 게 맞아")

- 대시보드 지표 카드 4개 → 3개 (총 완료 · 평균 점수 · 심화 진단율)
- `Stats` 인터페이스에서 `ctaRate` 제거
- RPC는 건드리지 않는다 — 화면에서 안 쓰면 그만이고, RPC 수정은 레포 밖 작업이다
- **제거 이유를 대시보드 코드에 주석 한 줄로 남긴다.** 안 남기면 다음 사람이 "왜 CTA가 없지?" 하고 되살린다

### 2. 죽은 `getStats()` 삭제

`deepRate` 모집단 불일치도 함께 사라진다. `DiagnosticRow`·`getRecentResults`·`getTotalCount`는 실제로 쓰이므로 유지.

### 3. ref 배선 실증 (유입경로 카드의 선행 조건)

배포본에 `?ref=wiring-test`를 붙여 빠른 진단을 1회 완주하고, `diagnostic_results.utm`에 값이 들어가는지 확인한다.

- **들어가면** → 가설 (a) 확정. 4번으로 진행
- **안 들어가면** → 가설 (b) 확정. **먼저 배선을 고친다.** 카드는 그다음
- **실증 레코드는 지우지 않고 남긴다.** `ref=wiring-test`로 식별해 유입경로 카드 집계에서만 제외한다 — 지우면 배선이 돌았다는 증거가 같이 사라진다

원칙: *"수집된다고 말하기 전에 실제로 한 건 넣어본다."*
(웃는돌 — *"막았다고 말하기 전에, 막기 전엔 나왔다는 걸 먼저 재둔다"*의 역방향)

### 4. 유입경로별 완료 카드

- 데이터는 이미 조회 중(`getRecentResults`가 `utm`을 가져온다). **DB 변경 없음**
- 집계 키는 **`utm.ref` 우선, 없으면 `utm.utm_source`, 둘 다 없으면 `미상`** — 이 순서로 고정한다
- **utm 없는 건은 "미상"으로 그대로 노출한다.** 숨기면 채널 판단이 왜곡된다
- ref 표기 규칙:

| 경로 | ref 값 |
|---|---|
| 인스타 프로필 링크 | `?ref=ig` |
| 인스타 게시물별 | `?ref=ig-YYMMDD` |
| 카카오톡 채널 | `?ref=kakao` |

### 5. 표시 규칙 — 모든 숫자에 분모와 출처를 단다

> 심화 진단율 33% *(분모: 빠른 진단 완료 12건 · Supabase RPC)*

계보: 골프청년(심지훈) — *"한도를 막는 로직과 화면 게이지가 서로 다른 걸 보고 있었다. 기능적으로는 정상인데 사용자한테는 그냥 거짓말이다."*

이 규칙이 있으면 결함 A 같은 것이 화면 층위에서 먼저 걸린다.

## 안 하는 것 (명시)

| 안 함 | 이유 |
|---|---|
| **진입 단(`diagnostic_start`) 추가** | Vercel Analytics를 코드에서 읽는 경로가 없다. CLI 토큰 경로는 크리덴셜 가드가 차단(정당), Chrome 확장은 2회 무응답 |
| 자체 이벤트 테이블로 4단 일원화 | 분모가 주당 3건인데 인프라만 는다 |
| RPC `get_diagnostic_stats()` 수정 | 레포 밖. 화면에서 안 쓰면 되는 문제다 |
| RLS 수정 | 별도 작업 (아래 참조) |

### ⚠️ 이 설계가 확인하지 못한 것

**진입 대비 완주율을 재지 못했다.** 인스타에서 100명이 눌렀는데 3명만 완주한 건지, 애초에 3명만 눌렀는지 못 가른다.
따라서 **"유입이 병목"이라는 판정은 완료 건수에만 근거한 것이고, 화면 문제 가능성은 배제되지 않았다.**
Vercel Analytics 접근 경로가 생기면 가장 먼저 확인할 것.

### 🔴 별건 — Supabase RLS

`clients`(대표명·계약기간·월 피) · `coaching_records`(원본 녹취) 포함 **10개 테이블의 RLS가 꺼져 있다.** anon 키만 있으면 전체 행 읽기·수정 가능.
`diagnostic_results`만 켜져 있다. 2026-07-26부터 알려진 건이고 이 설계 범위 밖이다.
**정책 없이 RLS만 켜면 앱이 전부 막히므로** 접근 패턴 확인이 선행되어야 한다.
