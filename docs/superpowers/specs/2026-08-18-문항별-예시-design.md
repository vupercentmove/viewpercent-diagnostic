# 문항별 예시 추가 — 설계 (2026-08-18)

정본 참조: [진단 언어 원칙 (2026-07-25)](../../진단-언어-원칙-2026-07-25.md)

## 1. 목적

대표가 문항을 읽고 **"뭘 묻는 건지는 알겠는데 우리 상황이 어디에 해당하는지 모르겠다"**에서 막히는 것을 줄인다.

근거: 2026-08-17 고객 시뮬레이션에서 나온 반응.

> "'장바구니 이탈 비율을 지금 바로 열어서 확인할 수 있나요' — 여기서 짜증이 났어요.
> 못 하니까 진단받는 건데 못 한다고 답하게 만드네요."

문항 자체는 사실 확인형으로 잘 다듬어져 있다(2026-07-25 개편). 부족한 것은 **"그 사실을 어디서 확인하는가"**다.

## 2. 범위

| 대상 | 넣는다 | 안 넣는다 |
|---|---|---|
| 빠른 진단 10문항 | ✅ 문항별 예시 | |
| 심화·정밀 27문항 | ✅ 문항별 예시 | |
| 결과 화면 | ✅ 약점 단계 1개에만 해석 예시 | 6단계 전부 |
| 문항 문구 | | ❌ 건드리지 않음 |
| 리커트 전환(권고안 2~4단계) | | ❌ 별도 작업 |

## 3. 결정과 근거

| 결정 | 선택 | 이유 |
|---|---|---|
| 예시 단위 | **문항별** (37개) | 문항이 구체적(`장바구니 이탈률`)이라 단계 단위 예시는 4~5문항에 반복 노출되며 겉돈다 |
| 노출 방식 | **항상 표시** (문항 아래 작게) | 토글은 막힌 사람이 존재를 모른 채 지나칠 수 있다. 대신 한 줄로 짧게 유지해 27문항 피로를 억제 |
| 결과 화면 범위 | **약점 단계 1개** | 결과가 이미 길다(빠른 진단 2,419자). CTA 성격 버튼이 4개라는 지적도 있어 증량을 피한다 |
| 데이터 위치 | **별도 모듈** | `questions.ts`·`deep-questions.ts`의 `id`·`answerType`·`stageId`는 스코어링 불변식이다. 표시용 데이터를 섞으면 관심사가 엉킨다 |

## 4. 구조

### 4.1 데이터

```
lib/question-examples.ts
  QUESTION_EXAMPLE: Record<string, string>   // 문항 id → 예시 (37개)
  getQuestionExample(id: string): string     // 없으면 "" 반환

lib/stage-examples.ts
  STAGE_EXAMPLE: Record<number, string>      // stageId → 해석 예시 (6개)
  getStageExample(stageId: number): string
```

선례: `lib/full-deep-content.ts`의 `QUESTION_INSIGHT`가 같은 형태(문항 id → 문자열 맵).

### 4.2 표시 컴포넌트

```
components/QuestionExample.tsx
  props: { questionId: string }
  예시가 없으면 null 반환 (빈 자리 없음)
```

세 문항 화면(`QuizStage` · `DeepQuizStage` · `FullDeepQuizStage`)이 공유한다.
같은 것을 세 번 쓰지 않는 이유는 `lib/likert-scale.ts`로 앵커를 모은 것과 같다 — 세 경로가 어긋나는 것을 구조로 막는다.

**배치**: 문항 텍스트 바로 아래, 선택지 위.

### 4.3 결과 화면

- `components/PriorityCard.tsx` (빠른 경로 1순위 카드)
- `components/FullResultLayout.tsx` 의 "가장 먼저 볼 구간" 카드

두 곳에 `getStageExample(weakestStageId)`를 한 단락으로 넣는다.

## 5. 카피 원칙

`docs/진단-언어-원칙-2026-07-25.md`를 그대로 따른다.

**지킬 것**
- 확인 가능한 사실 — 경로·행동·세는 법 (예: "카페24 관리자 > 통계 > 장바구니 이탈")
- 한 문장, 짧게

**금지**
- 자기채점 부사(`충분히`·`전략적으로`·`적극적으로`·`의도적으로`)
- 명령형(`~하세요`) · 느낌표 · `무조건`/`꼭`
- 성과 약속(`~하면 더 팔립니다`)
- 특정 솔루션 단정 — 카페24·아임웹 등은 **예로만** 들고 그것만이 답인 것처럼 쓰지 않는다

**비유 체계**: `돌아서다`=고객 행동(원인) / `새다`=돈의 결과. 섞지 않는다.

## 6. 검증

| 항목 | 방법 |
|---|---|
| 문항 id 일치 | `QUESTION_EXAMPLE` 키 집합 == `QUICK_QUESTIONS` + `DEEP_QUESTIONS` id 집합 (테스트로 고정) |
| 단계 id 일치 | `STAGE_EXAMPLE` 키 == `STAGES` id 6개 |
| 금지어 | 전 예시 문자열 스캔 테스트 |
| 화면 | 세 경로 로컬 브라우저 완주 |
| 회귀 | `npm test` · `npx tsc --noEmit` · `npm run build` |

문항 id 일치 테스트가 핵심이다. 문항이 추가·삭제될 때 예시 누락을 바로 잡아낸다.

## 7. 열린 사안

**예시 43개(문항 37 + 단계 6) 초안은 Claude가 쓴다.** 카피 정본 기준으로 작성하되 브랜드 목소리는 최종적으로 사람이 확인해야 한다.

→ 구현 단계에서 초안 전체를 제시하고 승인받은 뒤 커밋한다. 승인 없이 배포하지 않는다.

## 8. 이 설계가 하지 않는 것

- 문항 수를 줄이거나 흐름을 바꾸지 않는다. 2026-08-17 시뮬레이션의 반증 조건("패널 과반이 결과 도달 전 이탈")은 **미충족**이었다 — 타깃 3명 전원 완주했다. 문항 흐름 개편은 근거가 없다.
- 예시가 정답을 알려주지 않는다. 어디서 확인하는지만 알려주고, 판단은 대표가 한다(언어 원칙 2 — 유도 금지).
